# Notes — Milestone 2 (Reliable Code Extraction)

Per `docs/next_plans/README.md` rule 5: documenting a deviation caught after implementation rather than reopening the milestone plan itself.

## `clear()`-on-bridge removed (post-implementation correction)

The original implementation (see the TDD plan's Task 3 Step 2, itself following the milestone plan's own text) cleared `CodeMirrorManager`'s cell store whenever `KaggleDomParser.extractCells()` reported its result came from the MAIN-world bridge (`getLastExtractionSource() === 'bridge'`), on the theory that a bridge sweep is a full, authoritative list of every cell in the notebook — so it's safe to drop stale entries (e.g. cells the user deleted) before re-syncing.

That theory was wrong. `pageExtractor.ts`'s `extractAllCells()` (the MAIN-world side of the bridge) still walks `document.querySelectorAll('.jp-CodeCell .cm-editor')` — it gets full CodeMirror document text for editors that _are_ mounted, but has no more visibility than the isolated-world DOM-scrape fallback into cells Kaggle hasn't mounted an editor for at all (i.e. scrolled far off-screen in a virtualized notebook). So on essentially every normal lint (bridge succeeds the vast majority of the time), `clear()` wiped the store's virtualized-out cells and the subsequent `syncCells(cells)` only re-added whatever was currently rendered — meaning the store never actually retained coverage for scrolled-away cells. That's the exact problem (F7) this milestone exists to fix, silently defeated on the normal operating path.

A whole-branch code review caught this. The fix (see the commit that added this note) removes the clear-on-bridge branch entirely — `runLinter` now always calls `codeMirrorManager.syncCells(cells)` (merge only), regardless of which extraction path ran. The accepted tradeoff: a cell the user deletes leaves a stale entry in the store until the page is reloaded, since DOM-based extraction can't distinguish "deleted" from "not currently rendered." A more sophisticated fix (querying the Jupyter notebook model for a true full cell list) was explicitly out of scope for this correction pass.

Two other Important-severity bugs were fixed in the same review pass, unrelated to the store-clearing design but found in the same milestone's code:

- The debounced auto re-lint `MutationObserver` fired on scroll, not just edits, because virtualized mount/unmount of `.cm-line` nodes is a `childList` mutation indistinguishable from a real edit. Fixed with a focus guard (`document.activeElement` must be inside `.cm-content`).
- `KaggleDomParser.extractCellsViaDomScrape`'s `cellIndex` counter skipped incrementing on markdown cells, so it diverged from `pageExtractor.ts`'s "index among all `.jp-Cell`" convention — corrupting cell sort order and reported cell numbers whenever both extraction paths wrote to the same notebook's store. Fixed by incrementing the index unconditionally once per cell.

## `cmView` CM6-API path never fires on live Kaggle DOM; extraction rewritten to read the Jupyter notebook model directly (post-implementation correction, found during the manual gate)

During Task 5's manual verification, the user reported errors appearing/disappearing as they scrolled through a real notebook (13 code cells, 200+ lines each). Live diagnostics against the actual page (DevTools console, both the `top` and `notebook-editor-cells` frame contexts) confirmed:

- `(editor as any).cmView` — the expando property `pageExtractor.ts`'s `getEditorView()` was built to read, inherited from `old-linter`'s "Method 1 (most reliable)" — **does not exist** on any `.cm-editor` element in Kaggle's current live DOM (`cmView.view present: false` for all 13 editors, tested at multiple scroll positions). So the primary "read the full CM6 document via API" path never fired even once; every extraction silently fell back to `.cm-line` DOM scraping.
- CodeMirror 6 itself only mounts `.cm-line` DOM nodes for lines near the current viewport, even within a single, always-mounted `.cm-editor` (confirmed: the same cell's rendered `.cm-line` count varied between 1 and 86 across different scroll positions and lint runs, for cells whose real content ran to hundreds of lines). So the DOM-scrape fallback only ever captured whichever slice of a long cell happened to be scrolled into view at extraction time — the exact F3(b) truncation problem this milestone was supposed to close, still open.
- `.jp-Cell` wrapper elements (unlike their inner CodeMirror content) do **not** get virtualized out of the DOM — all 14 stayed mounted at every scroll position tested, with stable `data-uuid` values. This ruled out cell-identity/store-key instability as a contributing cause.
- Kaggle's notebook iframe (`kkb-production.jupyter-proxy.kaggle.net`, distinct from the outer `www.kaggle.com` frame) exposes `window.jupyterapp`, a real JupyterLab `Application` instance. `jupyterapp.shell.currentWidget.content.widgets` is the live array of cell widgets; each widget's `model.sharedModel.getSource()` returns that cell's complete source text (verified: consistently the cell's full length, e.g. 34,840 characters, regardless of scroll position or what was DOM-rendered), `model.type` is `'code'`/`'markdown'`, and `model.id` is a stable per-cell UUID independent of the DOM.

This is the "give the MAIN-world extractor access to the JupyterLab notebook model" option the whole-branch review had flagged as the _correct_ but harder fix and explicitly deferred (see the section above) — live testing showed the simpler fix wasn't sufficient (F3(b) was still open), so this correction implements it. `pageExtractor.ts` now tries `extractViaJupyterModel()` first (reads `window.jupyterapp`'s notebook widgets directly — full text, correct type filtering, stable ids, and inherently immune to scroll position since it never touches rendered DOM at all) and only falls back to the old DOM-based `extractAllCellsViaDom()` (CM6-API attempt, then `.cm-line` scraping) if `window.jupyterapp` isn't reachable in that frame — which is expected and harmless for the outer `www.kaggle.com` frame the content script also injects into (F17), since that frame has no notebook and the DOM fallback there already correctly reports zero cells.

A second, independent bug surfaced by the same live testing: the auto-relint focus guard (added in the correction above) checked "is focus anywhere inside _any_ `.cm-content`," not "is focus inside the specific cell that just mutated." Once a user clicks into any cell to edit, focus persists there through subsequent scrolling (scrolling doesn't blur an editor), so a virtualization-driven mutation in a completely different, unfocused cell still passed the guard — explaining why every log line during pure scrolling read "Auto re-lint after edit." Tightened to compare the mutated element's own `.closest('.cm-content')` against `document.activeElement`'s, so only a mutation inside the actually-focused cell schedules a re-lint.

Both fixes verified with `npm run type-check && npm run build` (both exit 0). Re-verification against the live notebook confirmed the fix: error count held stable (356) across many subsequent relints and scroll positions, where it had previously fluctuated between roughly 99 and 356 depending on scroll position and which extraction path/slice was captured.

## Unreproduced: a one-time 2x error-count jump (178 → 356) on one re-verification pass

One re-verification run showed the first automatic lint report 178 errors, then a later trigger (auto re-lint on edit) report exactly 356 — precisely double, confirmed by the user to be a literal duplicate of a specific error (an `undefined_var` in the last cell appeared twice in the overlay's list), not additional genuine content being found. The initial hypothesis — that Kaggle's async notebook-content blob fetch (`GET .../download/storage/kaggle-kernel-blobs/...`, observed racing page load) left some cells' `sharedModel` unhydrated on the very first pass, undercounting — was **wrong**: 178 was the correct, complete count, and 356 was 178's errors counted twice, most likely from the same physical cell landing in `CodeMirrorManager`'s store under two different keys (e.g. if `model.id` from `jupyterapp.shell.currentWidget.content.widgets` doesn't stay stable across two separate reads — JupyterLab 4.1's windowed/virtual notebook rendering, referenced directly in a deprecation warning seen in the same session, can recycle cell widget instances, which could plausibly regenerate widget-level state between reads even when the underlying document is unchanged).

This was **not confirmed** — five follow-up attempts (relinting, scrolling, editing) all reported the correct, stable 178 with no duplication. Per systematic-debugging discipline (no fix without a confirmed root cause; don't chase a non-reproducing symptom), no code change was made for this specific report. The "catch-up lint" added in the commit that first observed this (`ContentApp.tsx`'s initial-lint effect, a second one-time lint 4s after settings load) is **kept** — it's low-risk (one extra call through the same `isLintingRef` mutex every other trigger already uses) and was never confirmed to be the cause of the duplication, only correlated with the one session in which it was observed. If this resurfaces, the next diagnostic step is comparing `jupyterapp.shell.currentWidget.content.widgets.map(w => w.model.id)` across two reads to check `model.id` stability directly, and/or instrumenting `CodeMirrorManager` to log when `syncCells` adds a genuinely new key for a cell whose code closely matches an existing entry.
