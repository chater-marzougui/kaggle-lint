## Deviations from the milestone plan's original text, found during P1 expansion (2026-07-10)

- **Task 3**: the milestone plan cites `PopupApp.tsx:351` for the version footer; the real line was 272.
- **Task 4**: the milestone plan's "Interfaces" note asks whether to collapse `OverlayProps.errors[]`'s inline type into `LintError & {...}` — this was already done by Milestone 7/8 (`LintUIError extends LintError`, with a `uuid` field). Task 4 ended up narrower than the milestone plan's text: just deleting the duplicated `Severity`/`LintError` base interfaces.
- **Task 4 (TDD plan bug, found by the implementer during execution)**: the TDD plan's prescribed one-line replacement (`export type { Severity, LintError } from '@kaggle-lint/core';`) does not compile, because a bare re-export doesn't bind names into local scope, and `types/index.ts`'s untouched `LintUIError extends LintError` needs `LintError` in local scope. Fixed by the implementer using two statements (`import type {...}` + `export type {...}`) instead; independently verified via an isolated `tsc` repro during task review.
- **Task 6**: the milestone plan cites `README.md:42-45` for the Node.js prerequisites; the real lines were 29-30. Running `eslint` per-package (never possible before this task, since `npm run lint` was a silent no-op — F4) surfaced real, previously-invisible **errors**, not just the anticipated `no-explicit-any` warnings: 3× `prefer-const` (two bridge-request timeout patterns in `lineMarkers.ts`/`KaggleDomParser.ts`) and 2× a missing `eslint-plugin-react-hooks` registration (the existing `eslint-disable-next-line react-hooks/exhaustive-deps` comments referenced a rule ESLint didn't know about). Both had to be fixed within this task, not deferred, because `.github/workflows/ci.yml`'s lint job already calls `npm run lint` — adding real per-package scripts flips that job from no-op to enforcing on the very next push.
- **Task 6 (ui-components packaging, F23)**: the milestone plan leaves the `main`/`types` decision open. Tested empirically (not just reasoned about): pointing `main`/`types` at `src/index.ts` looked like the obvious fix (matches webpack's own `resolve.alias`), but `packages/extension/tsconfig.json` directly `include`s ui-components' `composite: true`-marked src tree, which triggers a `TS6305` composite-project error requiring a real, up-to-date `dist/**/*.d.ts` regardless of what `package.json`'s fields say. Kept `main`/`types` pointing at `dist/`, and fixed the concrete bug F23 actually names instead (missing CSS in `dist/`) via a `copyfiles` step mirroring `packages/core`'s existing `copy-pyodide` pattern.
